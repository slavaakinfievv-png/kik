# Структура Telegram-бота

`bot.py` теперь только совместимая точка входа: существующий запуск `python bot.py` сохраняется. Основная логика находится в пакете `app/`.

| Файл | Ответственность |
|---|---|
| `app/config.py` | `.env`, ID администраторов, путь БД, логирование |
| `app/runtime.py` | единый `Router` aiogram |
| `app/states.py` | FSM-состояния анкеты |
| `app/questions.py` | вопросы, лимиты, варианты ответов, причины отказа |
| `app/database.py` | SQLite, заявки, история, служебные настройки |
| `app/diagnostics.py` | обработка исключений и traceback |
| `app/services.py` | синхронизация карточек STAFF с данными БД |
| `app/ui.py` | клавиатуры, тексты карточек, отображение шагов |
| `app/handlers/user.py` | `/start`, кабинет, статус, история пользователя |
| `app/handlers/form.py` | заполнение, назад, редактирование, отправка анкеты |
| `app/handlers/decisions.py` | принятие/отклонение заявки и восстановление контакта принявшим администратором |
| `app/handlers/admin.py` | админ-панель, поиск, очистка и управление заявками |
| `app/handlers/customization.py` | тексты вопросов, стили и Premium Emoji |
| `app/main.py` | сборка приложения и polling |

## Где исправлять типовые проблемы

- вопрос или переход анкеты — `app/handlers/form.py` + `app/questions.py`;
- кнопка/текст интерфейса — `app/ui.py`;
- принятие/отказ и повторное получение контакта — `app/handlers/decisions.py`;
- админ-панель — `app/handlers/admin.py`;
- кастомизация — `app/handlers/customization.py`;
- сохранение/поиск заявки — `app/database.py`;
- падение/traceback — `app/diagnostics.py`;
- запуск и переменные окружения — `app/config.py`, `app/main.py`.

## Правило зависимостей

Обработчики могут использовать `database`, `ui`, `questions`, `states` и `services`. Низкоуровневые модули не должны импортировать handlers. Это уменьшает риск циклических импортов и делает локальные исправления безопаснее.

## Защита логики анкеты

- callback-кнопки привязаны к `session_id` активной анкеты;
- кнопка «Назад» дополнительно привязана к номеру текущего вопроса, поэтому старая кнопка из сообщения этой же сессии не может отмотать более поздний шаг;
- общий обработчик текстовых ответов не перехватывает Telegram-команды (`/start`, `/cancel`, `/status` и другие);
- индексы вариантов ответа проверяются явно и не допускают отрицательные Python-индексы;
- повторная отправка и конкурентные решения защищены транзакциями SQLite;
- если заявка удалена администратором во время отправки в STAFF, бот не подтверждает пользователю несуществующую заявку и удаляет осиротевшую STAFF-карточку;
- callback «Отправить» получает быстрый ответ до медленного сетевого этапа;
- при принятии STAFF получает фактический результат доставки контакта, а не сообщение об успехе до сетевой попытки;
- если контакт принятого кандидата не удалось доставить администратору, принявший заявку администратор может повторно получить его в личном чате командой `/contact <номер>`.

## Проверка

GitHub Actions устанавливает реальные зависимости, компилирует `bot.py`, весь пакет `app/` и тесты, импортирует приложение и запускает полный `unittest`-набор на Python 3.11 и 3.12.

`tests/test_logic.py` проверяет отдельные критические правила БД/FSM.

`tests/test_e2e.py` имитирует полный пользовательский и административный путь с временной SQLite-базой и фейковым Telegram Bot API:

- заполнение всех 11 вопросов и отправка заявки в STAFF;
- принятие заявки, обновление STAFF-карточки, контакт администратору и уведомление кандидату;
- повторное нажатие старой кнопки принятия;
- отказ и возможность новой подачи;
- старые кнопки ответа и «Назад» внутри активной анкеты;
- безопасное поведение старых кнопок после рестарта FSM;
- корректный STAFF-статус, если контакт после принятия не удалось доставить в личные сообщения.

На текущем наборе выполняются 15 тестов; полный прогон успешно проходит на Python 3.11 и 3.12.

## Рестарт процесса

Текущий FSM использует стандартное хранилище `Dispatcher()` в памяти. Поэтому незавершённые ответы не переживают полный рестарт процесса. Это не повреждает уже отправленные заявки: старые кнопки становятся безопасно неактивными, а пользователь может начать заполнение заново. Для сохранения незавершённой анкеты между рестартами потребуется отдельное постоянное FSM-хранилище (например Redis или собственное SQLite-хранилище).
